# 검수 절차 v2

v2는 v1 dev 검증(2026-09-29)에서 확인한 문제를 반영한 판정 절차다. **API 호출 수는 v1과 같다**
(루브릭 방식: 항목 수 + 1회, 자유형: 2회). v1 프롬프트와 v1 결과는 그대로 남아 있으며
`--prompt-set v1`로 재현할 수 있다.

## 선택

| 사용 위치 | 기본값 |
| --- | --- |
| `nonsul-review run`, `batch` | `--prompt-set v2` |
| `scripts/live_smoke.py` | `--prompt-set v2` |
| Python API `RunConfig` | `prompt_set="v1"` (기존 호출과 v1 기록 재현을 깨지 않기 위해) |
| 공개 실행 증거 검사(`release_check.py --require-live`) | v2만 허용 |

결과의 `meta.prompt_version`은 `rubric-v2` 또는 `free-v2`이고, `meta.prompt_sha256`에는
`common-v2.txt`와 해당 방식의 v2 프롬프트 두 개의 해시가 기록된다.

## v1에서 바뀐 점

### 두 방식 공통 (`common-v2.txt`)

1. **독자 분리**: `reason`은 강사용이고 "~다"체로 쓴다. `feedback`과 `overall_feedback`은
   학생용이고 "~습니다"체로 쓰며, 루브릭 ID, 판정값, 점수, 강사에게 하는 말을 넣지 않는다.
2. **인용 경계**: 답안 원문의 정확한 연속 부분 문자열이되, 완결된 문장이나 수식 단위로 고른다.
   수식 구분자, LaTeX 명령, 중괄호 구조의 중간에서 시작하거나 끝내지 않으며, 경계를 맞추려고
   문자를 덧붙이지 않는다.
3. **누락 지적**: 인용할 수 없는 필수 단계의 누락도 지적한다. 무엇이 필요하고 무엇이 없는지 쓴다.
4. **보완 설명 검산**: 새로 쓰는 식, 조건, 구간, 논증을 검산한다. 부호, 구간 끝점, 등호 조건,
   그 논증이 실제로 보이는 명제(하한과 유일성의 구분 등)를 확인한다.
5. **보완 요구 억제**: 충족 항목에는 보완점을 억지로 만들지 않고 유용할 때만 최대 1개를 쓴다.
   결론이 맞아도 핵심 근거가 빠졌다면 선택 사항이 아니라 필요한 수정이다.
6. **검토 필요 표시**: 강사 판단이 필요한 항목은 문장이 아니라 `needs_review`로 표시한다.

### 방식별

- **루브릭 방식 마지막 단계**: 전체 피드백은 항목별 판정·이유·피드백을 중심으로 종합하고
  새로운 풀이나 보완 논증으로 확장하지 않는다. 종합 중 발견한 항목 판정의 오류, 근거 부족,
  항목 간 모순은 판정을 바꾸지 않고 `review_flags`에 기록한다.
- **자유형 첫 단계**: 지적은 답안의 실제 서술 또는 전체 답안에서 확인한 필수 논증의 누락에 근거한다.
- **자유형 마지막 단계(판정표)**: 앞서 쓴 전체 피드백을 고칠 수 없다. 그 안의 수학적 오류,
  판정과의 모순, 강사 확인이 필요한 내용을 `review_flags`에 기록한다.

## `review_flags`

v2 마지막 단계는 `review_flags` 키를 반드시 반환한다. 검토 사항이 없으면 `[]`를 반환하며, 키 자체를
누락하면 검증 실패로 처리한다(코드가 빈 목록을 대신 채우지 않는다). 각 항목은
`{"rubric_id": "...", "note": "..."}`이다.

| 규칙 | 동작 |
| --- | --- |
| 루브릭에 없는 ID, 공백뿐인 메모, 필드 누락, 추가 키 | 단계 검증 실패 (재시도 대상) |
| 같은 ID의 여러 메모 | 모두 보존 |
| 해당 항목의 `needs_review` | 기존 값 OR 메모 존재 |
| 판정값, `reason` | 변경하지 않음 |
| 메모 | 결과의 `review_flags`에 별도 보존 |
| raw | 모델 응답 원본 그대로 |

`review_flags`는 **자동 수정 장치가 아니다.** 자유형에서 앞의 전체 피드백이 틀렸다는 메모가
붙어도 그 피드백은 결과에 그대로 남는다. 메모가 붙은 결과는 강사가 확인·수정·확정하기 전
학생에게 전달하지 않는다.

- `review` 명령이 만드는 검수 YAML의 각 항목에 `model_review_flags`(읽기 전용)가 표시된다.
- `finalize`는 원본 `review_flags`를 확정본에 그대로 두고, 변경 기록에 항목별 메모와
  `model_review_flag_count`를 남긴다.
- 공개 실행 증거 검사는 마지막 단계 응답의 `review_flags`가 결과와 같은지,
  메모가 붙은 항목이 `needs_review`인지 확인한다.

## 탐색적 평가 항목

v1 dev 검토에서 판정값 외의 문제가 발견되어 다음을 사람이 기록한다.

| 지표 | 기록 방법 |
| --- | --- |
| 피드백의 수학적 문제 | 명시적 오류와 논증 불충분을 구분하고, 해당 구절과 수정 근거를 기록 |
| 결과 내부 모순 | 전체 피드백과 항목 판정·이유가 양립하지 않는 사례 |
| 불필요한 보완 요구 | 이미 있는 내용의 반복 요구, 충분한 서술에 대한 추가 요구를 요구 단위로 셈 |

## 재실행 기록의 이름

- **v1·v2 검수 절차 비교**: 같은 입력을 v2로 다시 실행한 것. 프롬프트뿐 아니라 마지막 단계의
  응답 형식과 결과 조립도 함께 바뀌므로 "프롬프트만 바꾼 비교"가 아니다.
- **v2 개정 기준·개정 답안 확인**: 루브릭 문구나 답안을 개정한 입력을 v2로 실행한 것.

평가(`evaluate`)는 같은 버전 안의 rubric/free만 짝지어 비교한다. v1과 v2, 그리고 개정 기준·개정 답안의
결과는 서로 다른 실험 회차이므로 **각각 별도의 결과 폴더에 두고 따로 평가한다.** 한 폴더에 버전이
섞이면 평가 보고서에 경고가 남는다.
